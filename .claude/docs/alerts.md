# Alerts

An alert is a row in the BOA-owned `alerts` table. It flags one student (`sid`) for one condition in one term. Alerts are **generated** by the cache refresh job from data loch and Canvas analytics data; no user creates them. Each advisor can **dismiss** an alert for themselves, which is recorded in `alert_views`. Read paths only show alerts that are active (`deleted_at IS NULL`) and whose `key` starts with the **current** term ID.

Model: `boac/models/alert.py` (`Alert`). Per-viewer dismissals: `AlertView` in `boac/models/db_relationships.py`.

Don't confuse student alerts with `alertScreenReader` (`src/lib/utils.ts`) or `DismissibleFooterAlert.vue` / service announcements. Those are screen-reader and banner features.

## Alert types

Every type below is generated by `Alert.update_all_for_term(term_id)`. Messages are plain strings built when the alert is generated.

| `alert_type` | Trigger | Source data | `key` | Message |
|---|---|---|---|---|
| `midterm` | A section has `midtermGrade` and no final `grade` (`update_alerts_for_enrollment` → `update_midterm_grade_alerts`) | `student_enrollment_terms.enrollment_term` JSON (`data_loch.get_enrollments_for_term`) | `{term}_{ccn}` | `{displayName} midpoint deficient grade of {grade}.` |
| `no_activity` | The latest Canvas `lastActivity.student.raw == 0` and `roundedUpPercentile <= ALERT_NO_ACTIVITY_PERCENTILE_CUTOFF` | `canvasSites[].analytics.lastActivity.student` in the same enrollment JSON | `{term}_{displayName}` | `No activity! Student has never visited the {displayName} bCourses site for {termName}.` |
| `infrequent_activity` | `raw > 0`, days since last activity `>= ALERT_INFREQUENT_ACTIVITY_DAYS`, and percentile `<= ALERT_INFREQUENT_ACTIVITY_PERCENTILE_CUTOFF` | same | `{term}_{displayName}` | `Infrequent activity! Last {displayName} bCourses activity was {N} days ago.` |
| `withdrawal` | `sisProfile.withdrawalCancel.termId == term_id`. Runs only when `ALERT_WITHDRAWAL_ENABLED` is on and `term_id` is the current term | `student_profiles.profile` for active students (`data_loch.get_active_student_profiles`) | `{term}_withdrawal` | `Student is no longer enrolled in the {termName} term.` |
| `academic_standing` | The student's standing row for `term_id` has status `DIS`, `PRO`, or `SUB` | `academic_standing` (`data_loch.get_academic_standing` via `merged/student.get_academic_standing_by_sid`) | `{term}_{actionDate}_academic_standing_{status}` | `Student's academic standing is '{description}'.` (`ACADEMIC_STANDING_DESCRIPTIONS` in `boac/lib/berkeley.py`) |

Eligibility and gating:

- Only sections that pass `section_is_eligible_for_alerts()` (`boac/lib/berkeley.py`) are considered. Lecture sections always pass. Other sections are skipped when the course `displayName` looks like a DeCal or independent-study number (`1?9[89][A-Z]?[A-Z]?$`).
- Sections that already have a final `grade` get no enrollment alerts.
- `no_activity_alerts_enabled()` and `infrequent_activity_alerts_enabled()` require the config flag to be on and the current term not to be Summer. They also require enough days since `term_begins` (`data_loch.get_undergraduate_term`): `ALERT_NO_ACTIVITY_DAYS_INTO_SESSION` for no activity, `ALERT_INFREQUENT_ACTIVITY_DAYS` for infrequent activity.
- Config defaults are in `config/default.py` (14 days, 20th percentile, all enabled). `config/test.py` turns off infrequent-activity and withdrawal alerts.

**Not generated by current code:**

- `late_assignment` and `missing_assignment` appear only as hand-made rows in the `create_alerts` test fixture.
- Holds are **not** alerts. `put_notifications()` (`boac/api/util.py`) reads `data_loch.get_sis_holds` and returns holds as `notifications.hold` with `read: True`.
- There is no "low grade" alert. `isAlertGrade()` (`src/lib/berkeley-utils.ts`) is only a UI icon on the course page, and `low_assignment_scores` (`boac/merged/advising_notes_reports.py`) is an admin report.

## Data model (`scripts/db/schema.sql`)

```sql
alerts (id serial PK, sid varchar(80), alert_type varchar(80), key varchar(255),
        message text NOT NULL, deleted_at timestamptz, created_at, updated_at)
  UNIQUE (sid, alert_type, key, created_at)   -- alerts_sid_alert_type_key_created_at_unique_constraint
  INDEX alerts_deleted_at_idx, alerts_sid_idx
alert_views (alert_id FK alerts ON DELETE CASCADE, viewer_id FK authorized_users ON DELETE CASCADE,
             created_at, dismissed_at)
  PK (alert_id, viewer_id); INDEX on dismissed_at, viewer_id
```

- **Active** means `deleted_at IS NULL`. **Deactivated** means `deleted_at` is set (`deactivate`, `deactivate_all`, `deactivate_all_for_term`). Rows are never hard-deleted.
- **Term scoping is done through `key`.** Every generated key starts with `{term_id}_`, and every read query filters with `key LIKE current_term_id() + '_%'`. There's no `term_id` column.
- `created_at` is part of the unique constraint, so the same `(sid, alert_type, key)` can have several rows over time.
- `Alert.create()` falls back to a key of today's date (`YYYY-MM-DD`) and raises `ValueError` on a blank key. A date key never matches the term filter, so that alert is never shown.
- `viewer_id` is `authorized_users.id`, not a UID.

## Lifecycle: the refresh job

```
GET /api/admin/cachejob/refresh  (@admin_required; scripts/refresh_current_term_cache.sh calls it with an App-Key header; also the `flask refresh_external_data` CLI)
  → cache_utils.refresh_request_handler(term) → background Thread → background_thread_refresh
  → load_term(term_id)        # term_id='all' → load_all_terms() loops all_term_ids()
      → refresh_alerts(term_id)
          → Alert.deactivate_all_for_term(term_id)      # bulk soft-delete; bumps updated_at
          → Alert.update_all_for_term(term_id)          # regenerate from the loch
          → json_cache.clear('alert_counts_curated_group_%'); re-stow counts for each default-domain group's owner
      → (current term only) ... load_filtered_cohort_counts()  # resets every cohort's sids/student_count/alert_count and recomputes for the owner
```

- BOA has no in-app scheduler. Something outside BOA calls the endpoint or script on a schedule (where that cron lives is unverified).
- **Reactivation, not recreation.** `create_or_activate()` looks up the most recently updated row with the same `(sid, alert_type, key)` and reuses it (clears `deleted_at`, sets the new `message`) when either:
  - the row was updated in the last **2 hours**, meaning it was deactivated earlier in this same run, or
  - `force_use_existing=True` is passed (academic standing does this).

  Otherwise it inserts a new row. Reusing the row keeps the alert `id`, which is what lets per-viewer dismissals survive a refresh.
- `preserve_creation_date=True` keeps `updated_at == created_at`. Midterm, withdrawal, and academic standing alerts use it, and academic standing alerts also set `created_at = actionDate` on a new row. No-activity and infrequent-activity alerts get a fresh `updated_at` on every run.
- Alerts are recalculated for whichever term ID is passed in, but only the current term is ever shown.

## API

| Endpoint | Decorator | Behavior |
|---|---|---|
| `GET /api/alerts/<alert_id>/dismiss` (`boac/api/alerts_controller.py`) | `@advisor_required` (see `.claude/docs/permissions.md`) | `Alert.dismiss()` upserts an `AlertView` with `dismissed_at=now()` (repeat calls are fine), then calls `CohortFilter.refresh_alert_counts_for_owner(user_id)` and `CuratedGroup.clear_cached_alert_counts_for_owner(alert_id, user_id)`. An unknown id returns 400 |
| `GET /api/cohort/<id>/students_with_alerts` | `@advisor_required` | Profile summaries plus `alertCount` for students with active, undismissed alerts |
| `GET /api/curated_group/<id>/students_with_alerts` | `@advisor_required` | The same, for a curated group |

**There is no undismiss endpoint.** A dismissal applies only to that viewer; other advisors still see the alert.

## Where counts appear

Every count means active, current-term alerts that **this viewer** hasn't dismissed.

| Surface | Function | Caching |
|---|---|---|
| Student page timeline | `put_notifications()` → `Alert.current_alerts_for_sid(viewer_id, sid)`, returning `{id, alertType, key, message, createdAt, updatedAt, dismissed}` plus `read` (= `dismissed`) and `type: 'alert'` | none |
| Cohort `alertCount` (Home, cohort page) | `CohortFilter.to_api_json(include_alerts_for_user_id=…)` → `Alert.current_alert_counts_for_sids` | Stored in `cohort_filters.alert_count`, written only when it's `None`. `refresh_alert_counts_for_owner` rewrites it after a dismissal. See `.claude/docs/cohorts.md` |
| Curated group `alertCount` | `alert_counts_for_curated_group()` (`boac/api/util.py`) → `Alert.current_alert_counts_for_curated_group(count_only=True)` | `@stow('alert_counts_curated_group_{group_id}_user_{viewer_id}')`. Cleared when students are added or removed, on dismissal, and by `refresh_alerts` |
| Student lists: course page, search, cohort and group rows | `course_controller._include_alert_counts`, `search_controller` + `add_alert_counts`, `curated_group_controller._include_alert_counts` | none for course and search |

`Alert.alert_counts_by_query()` returns `[{sid, alertCount}]` when `count_only=True`. When `count_only=False` it also calls `data_loch.get_basic_student_data(sids)`.

## Frontend

- `dismissStudentAlert(alertId)` in `src/api/student.ts` calls `GET /api/alerts/{id}/dismiss`. `getStudentsWithAlerts` is in both `src/api/cohort.ts` and `src/api/curated.ts`.
- **Dismissing.** `AcademicTimeline.vue` builds the "Alerts" tab from `student.notifications.alert`. In `AcademicTimelineTable.vue`, opening a message calls `open()` → `markRead()`, which calls `dismissStudentAlert` for unread `alert` messages. There's no separate dismiss button: **expanding the alert is the dismissal.** Holds arrive with `read: true`, so they never trigger a call. "Expand all" is offered only for the appointment, eForm, and note tabs, so it never dismisses alerts in bulk.
- **Counts in lists.**
  - `StudentAvatar.vue` shows a badge: the visible number is `aria-hidden`, with `sr-only` text "N alerts".
  - `SortableStudents.vue` has an "Alerts" column. Its badge has `aria-label` "No alerts" / "N alerts", and sorting announces the change with `alertScreenReader`.
  - `SortableGroup.vue` (Home) shows the group's `alertCount` and loads `students_with_alerts` when expanded.
- **Accessibility.** Collapsed timeline rows are `role="button"` with `tabindex=0`, open on `@keyup.enter`, and expose `aria-expanded` / `aria-controls`. The full message is in an `sr-only` span. `AcademicTimelineCategory.vue` renders the "Alert" pill with `sr-only` text. Keep these patterns when changing the timeline (see `src/CLAUDE.md`).

## Gotchas

- **Current term only.** Every read query uses `current_term_id()`. Alerts generated for another term are stored but never shown.
- **The two-hour reuse window.** If more than 2 hours pass between `deactivate_all_for_term` and the moment a student is processed in `update_all_for_term`, non-academic-standing alerts are inserted as new rows with new ids, and earlier dismissals no longer apply.
- **Shared key format.** `no_activity` and `infrequent_activity` use the same key format (`{term}_{displayName}`); only `alert_type` tells them apart.
- **Cached cohort counts lag.** `cohort_filters.alert_count` is recomputed only when it's `None`. New alerts show up in cohort counts only after `load_filtered_cohort_counts()` (current-term refresh), a dismissal by the owner, or a change to a referenced curated group (`_refresh_related_cohorts`).
- **Viewer ID, not UID.** `current_alerts_for_sid` and the count queries take `viewer_id` = `authorized_users.id`.
- **Dismissal is a GET and fires on expand.** Any code that opens timeline messages programmatically (e.g. `scrollToPermalink`) dismisses alerts as a side effect.
- **Past-term gating uses the current term.** The no-activity and infrequent-activity gates check the *current* term's start date and name, even when `update_all_for_term` runs for another term.
- **Unused helpers.** `Alert.get_alerts_per_date_range` and `Alert.deactivate_all` have no callers outside tests (unverified for scripts).
